# Auto-Rollback Orchestrator (ARM MCP PoC - SRE-PoC-4)

A Copilot CLI / VS Code chat agent that watches a single Azure Resource Manager
deployment, evaluates a fixed post-deploy health gate, and - on breach or
failure - **cancels** the deployment and re-deploys the **last-known-good (LKG)
template** automatically. Backed by the
[Azure Resource Manager MCP Server](https://aka.ms/JoinARMMCP).

## Why this exists

A bad ARM deploy that "succeeds" but leaves the resource group in a half-broken
state (resources stuck `Failed`, public IPs accidentally exposed, untagged
resources, etc.) is the kind of incident that costs hours of on-call time. This
PoC turns that response into a deterministic, auditable, **operator-gated**
loop: detect → confirm → cancel → roll back → re-verify - with an
incident-ready timeline written to disk every run.

Two design choices make it safe to put in a real on-call workflow:

- **No LLM judgement on critical decisions.** Health-gate KQL is read verbatim
  from `rules/rules.yaml`. Rollback is bounded by an integer cap. Run IDs hash
  the ruleset.
- **Every destructive action requires an explicit `YES`.** The agent will halt
  and write a `HALTED` report rather than proceed without confirmation.

## Intended end state

Every run terminates in **exactly one** of four overall statuses, written into
`exports/rollback-<run_id>.md`:

| Overall status | When you see it | Azure side-effects |
|---|---|---|
| `SUCCEEDED` | Deployment settled `Succeeded` AND health gate R001-R004 all PASS. | None. The new deployment stays. |
| `ROLLED_BACK` | Deployment failed / timed out / breached the gate, operator confirmed `YES`, LKG re-deploy passed the health gate within `max_rollback_attempts`. | `cancel_arm_template_deployment` invoked. LKG re-deploy is `[SIMULATED]` in v1 (see [Determinism Deviation](#determinism-deviation)). |
| `HALTED` (`reason=user-declined-cancel`) | Cancel prompt was shown and the operator did not reply `YES`. | None. |
| `HALTED` (`reason=max-rollback-attempts-reached`) | LKG re-deploy failed the health gate twice in a row (or `max_rollback_attempts` times). | Original deployment cancelled; LKG re-deploys were `[SIMULATED]`. Operator intervention required. |

The orchestrator never proceeds past Step 5 without an explicit `YES`, and
never invokes `create_template_deployment` in v1 - so the worst-case outcome
of any run is `HALTED` with a full timeline and no destructive Azure calls.

## What it does

1. Loads runbook config (`runbooks/prod.yaml`) - subscription, resource group, deployment
   name, LKG template ref, and gate parameters.
2. Polls `get_arm_template_deployment_status` until the deployment reaches a terminal state
   or `health_gate_timeout_seconds` elapses.
3. Runs the fixed health gate (`rules/rules.yaml`) in **rule_id order** via `execute_query`.
4. On PASS → emits `SUCCEEDED` report and stops.
5. On FAIL or timeout → requests user confirmation, then calls `cancel_arm_template_deployment`,
   fetches the LKG template from `last_good_template_ref`, and re-deploys.
6. Rollback attempts are bounded by `max_rollback_attempts` (default 2). On exhaustion,
   emits `STATUS=HALTED` and stops.
7. Renders a canonical timeline (`[timestamp_utc] ACTION: description (status)`) and
   a structured report to `exports/rollback-<run_id>.md`.

## Why the output is deterministic

- Queries are NOT generated by the LLM - they are read verbatim from `rules.yaml`.
- Timeline format is pinned: `[timestamp_utc] ACTION: description (status)` - one line per step.
- Run ID is deterministic: `ROLL-{YYYYMMDD}-{scope}-{sha256(rules.yaml)[:8]}`.
- Health gate evaluates rules in `rule_id` order (R001 → R002 → R003 → R004). No reordering.
- Rollback cap is an integer from the runbook (`max_rollback_attempts`). No LLM judgment.

## Determinism Deviation

> **This PoC does not include `validate_query` in its tool allowlist per source spec.**
> KQL correctness is assured by pre-testing during development. Operators running this PoC
> live should hand-verify `rules.yaml` KQL via the `validate_query` tool in another workspace
> if uncertain.
>
> **This PoC does not include `generate_query` in its tool allowlist.**
> All KQL is pre-defined as literal strings in `rules/rules.yaml`. The agent MUST read KQL
> verbatim from that file and MUST NOT derive, generate, or paraphrase queries at runtime.
> Both exclusions are enforced by agent hard rules and by the absence of the tools from the
> `tools:` block in `auto-rollback.agent.md`.

## How it works (end-to-end flow)

1. **Chat routes the message.** VS Code sees `@auto-rollback watch`, loads
   `.github/copilot/agents/auto-rollback.agent.md` as the system prompt.
2. **MCP server starts.** Runtime reads `.vscode/mcp.json`, connects to
   `https://mcp.management.azure.com`, handshakes, exposes 4 tools.
3. **Agent loads config.** Reads `runbooks/prod.yaml` + `prod.values.yaml` (substitution).
   Computes `run_id`.
4. **Agent polls deployment status.** Calls `get_arm_template_deployment_status` in a loop.
   Writes one timeline line per poll.
5. **Deployment settles.** On `Succeeded` → health gate. On `Failed`/`Canceled`/timeout →
   skip to cancel + rollback.
6. **Health gate.** For each rule R001→R004: call `execute_query` with literal KQL,
   record `PASS`/`FAIL`. On any FAIL → breach.
7. **Cancel flow.** User confirmation required. Calls `cancel_arm_template_deployment`.
   Writes audit log.
8. **Rollback.** Fetches LKG template. In v1: simulated (`[SIMULATED]`). Re-runs health
   gate. On second failure → `HALTED`.
9. **Output.** Renders report + timeline to chat and to `exports/rollback-<run_id>.md`.

## Install

1. Clone the catalog and open this PoC folder as a VS Code workspace. The ARM MCP server
   is declared in `.vscode/mcp.json` (VS Code will prompt to start it on first chat).

   ```powershell
   git clone https://github.com/jvargh/arm-mcp-poc-catalog.git
   code arm-mcp-poc-catalog/SRE-PoC-04-auto-rollback
   ```

   - If not yet authorized for the ARM MCP server: <https://aka.ms/JoinARMMCP>.
   - For GitHub Copilot CLI: copy the `Azure Resource Manager MCP Server` entry from
     `.vscode/mcp.json` into `~/.copilot/mcp.json`.
2. Sign in to Azure (`az login`) with **Reader** + **Resource Graph Reader** on the target
   scope. For actual deploys you also need **Contributor** on the target RG.

> MCP server entry (`.vscode/mcp.json`):
>
> ```json
> {
>   "servers": {
>     "Azure Resource Manager MCP Server": {
>       "type": "http",
>       "url": "https://mcp.management.azure.com"
>     }
>   }
> }
> ```

## Configure your scope

Copy and fill in the values file before first run:

```powershell
Copy-Item runbooks/prod.values.yaml.example runbooks/prod.values.yaml
```

Edit `runbooks/prod.values.yaml`:

```yaml
subscription_id: "sub-id"
resource_group: "aks01day2-rg"
deployment_name: "payments-deploy-20260512"
template_file: "infra/main.json"
parameters_file: "infra/main.parameters.json"
last_good_template_ref: "git:refs/heads/main:infra/main.json"
last_good_parameters_file: "infra/lkg.parameters.json"
```

The paired ARM template and parameters live in [`infra/`](infra/) (see
[`infra/README.md`](infra/README.md)).

Verify `.gitignore` excludes `prod.values.yaml` (the root `.gitignore` contains
`**/runbooks/*.values.yaml`).

## Worked example: last live run (2026-05-13)

The committed example in
[`exports/rollback-ROLL-20260513-prod-cd3bf2f8.md`](exports/rollback-ROLL-20260513-prod-cd3bf2f8.md)
is the **real** output of a watch run executed from this workspace - not a
simulation. It demonstrates the most common first-run failure mode and the
defensive design that makes it safe.

**What was configured**

- Scope: `prod`, RG: `aks01day2-rg`
- `deployment_name: payments-deploy-20260512` (a name that did not exist in the RG)
- `last_good_template_ref: git:refs/heads/main:infra/main.json`

**What happened (terminal state: `HALTED`, reason: `user-declined-cancel`)**

| Step | Observed |
|---|---|
| Run ID | `ROLL-20260513-prod-cd3bf2f8` (deterministic - `YYYYMMDD + scope + sha256(rules.yaml)[:8]`) |
| Poll #1 | `poll-error error="DeploymentNotFound: Deployment 'payments-deploy-20260512' could not be found in resource group 'aks01day2-rg'." (FAIL)` |
| Failure-handling rule | `get_arm_template_deployment_status` error → orchestrator routes to Step 5 (cancel flow) per SKILL.md "Failure handling". |
| Confirmation gate | Verbatim prompt: `Cancel deployment payments-deploy-20260512? This will stop all in-progress operations. Reply YES to confirm.` |
| Operator response | Anything other than `YES` → `cancel-aborted reason=user-declined (HALTED)`. |
| Health gate | All four rules `SKIPPED` (deployment never settled, so Step 4 was never entered). |
| Rollback attempts | `0 / 2` - never reached. |
| Azure side-effects | **Zero.** No `cancel_arm_template_deployment` call, no `create_template_deployment` call. |

**Takeaways for new operators**

1. **`DeploymentNotFound` is the most common first-run failure.** Run the
   pre-flight commands below before invoking `/watch`, or expect the run to
   land on this exact path.
2. **Declining the cancel prompt is always safe.** The orchestrator writes a
   `HALTED` report, leaves the cluster untouched, and exits cleanly. The
   timeline tells you exactly what it would have done.
3. **The run ID is reproducible.** Two runs on the same UTC day with the same
   scope and unchanged `rules.yaml` produce the same `run_id` - so re-running
   *appends* `_N` to the export filename rather than overwriting evidence.

## Pre-flight: make sure there is a deployment to watch

The orchestrator polls a named ARM deployment that must already exist (or be
in-flight) in the target resource group. If `deployment_name` does not exist,
the watch run will halt with `DeploymentNotFound` - exactly the path captured
in the [worked example](#worked-example-last-live-run-2026-05-13) above.

Pick **one** of the two paths below before running the agent.

### Option A: point at an existing deployment

List deployments in your target RG and copy a real name into `prod.values.yaml`:

```powershell
az deployment group list `
  -g aks01day2-rg `
  --query "[].{name:name, state:properties.provisioningState, ts:properties.timestamp}" `
  -o table
```

Set `deployment_name:` in `runbooks/prod.values.yaml` to one of the returned names.

### Option B: create a fresh deployment from `infra/`

Use the demo template shipped in [`infra/`](infra/) to start a new deployment,
then watch it. Pick a unique deployment name (the date-stamped convention works):

```powershell
$dep = "payments-deploy-$(Get-Date -Format yyyyMMdd)"

az deployment group create `
  --name $dep `
  -g aks01day2-rg `
  --template-file infra/main.json `
  --parameters infra/main.parameters.json `
  --no-wait
```

Then update `runbooks/prod.values.yaml`:

```yaml
deployment_name: "payments-deploy-20260513"   # use the value of $dep
```

> The `--no-wait` flag returns immediately so the orchestrator can poll the
> deployment while it is still `Running`.

## Run

Once `deployment_name` resolves to a real deployment, invoke the skill from
VS Code chat. The skill ships three slash-prompts under
`.github/copilot/skills/auto-rollback/prompts/`:

| Verb | Chat invocation | What it does |
|---|---|---|
| watch | `/watch deployment_name=payments-deploy-20260513 scope=prod` | Poll status, run health gate, auto-rollback on breach. |
| rollback | `/rollback scope=prod` | Manually re-deploy the LKG template (v1: simulated). |
| cancel | `/cancel deployment_name=payments-deploy-20260513 scope=prod` | Cancel an in-progress deployment after `YES` confirm. |

You can also talk to the agent directly with `@auto-rollback` and describe the
verb in natural language; the prompt files are the deterministic entry point.

After a run, the rendered report lands in `exports/rollback-<run_id>.md`.

## Acceptance criteria

| Criterion | Where it lives |
|---|---|
| Pulls last-good template from Git ref | `runbooks/prod.yaml` → `last_good_template_ref`; SKILL.md Step 6 |
| Configurable health gate (ARG) with timeout | `health_gate_timeout_seconds` in runbook; SKILL.md Steps 3–4 |
| Bounded rollback attempts | `max_rollback_attempts` in runbook; SKILL.md Step 6; agent hard rule #3 |
| Incident-ready timeline | `[timestamp_utc] ACTION: description (status)` in SKILL.md Steps 2–6 |
| Cancel path with per-deployment confirmation | SKILL.md Step 5; `prompts/cancel.prompt.md`; agent hard rule #4 |
| 4-tool allowlist (no derivation tools) | `auto-rollback.agent.md` tools block; agent hard rule #2 |

## Tool allowlist (exactly 4 tools)

| Tool | Purpose |
|---|---|
| `create_template_deployment` | Re-deploy LKG template (v1: simulated only) |
| `get_arm_template_deployment_status` | Poll deployment status during watch |
| `cancel_arm_template_deployment` | Cancel in-progress deployment |
| `execute_query` | Run literal health-gate KQL from rules.yaml |

`generate_query` and `validate_query` are **not** in the allowlist. See
[Determinism Deviation](#determinism-deviation).
