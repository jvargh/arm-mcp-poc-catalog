# Toil Killer: Weekly Drift + Cleanup PRs (SRE-PoC-12)

A Copilot CLI / VS Code chat agent that scans Azure weekly for orphaned resources and IaC drift,
then proposes a PR with corrective ARM patches and savings estimates — without ever deploying.

Backed by the [Azure Resource Manager MCP Server](https://aka.ms/JoinARMMCP).

## What it does

1. Loads a fixed rule pack (`skills/weekly-cleanup/rules/rules.yaml`) — 6 cleanup and
   drift-detection rules with **pre-canned ARG queries**.
2. For every rule: `generate_query` (if `generate_hint` is set) → `execute_query` (ARM MCP).
   No `validate_query` step — see [Determinism Deviation](#determinism-deviation).
3. Groups findings by category: **orphaned** → **drift** → **compliance**.
   Within each group, sorts by estimated monthly savings descending.
4. Composes a proposed PR with a categorized cleanup table, savings estimates, and ARM patch
   template references.
5. Writes the PR content as a markdown file to `exports/proposed-pr/`.

## Why the output is deterministic

- Queries are **literal KQL** read verbatim from `rules.yaml` — NOT generated by the LLM at run time.
- Sort order is pinned: category group order (orphaned → drift → compliance), then estimated savings
  descending, then `resource_id` ascending as tie-break.
- PR title format is pinned: `Weekly Azure cleanup: {orphan_count} orphaned, {drift_count} drifts,
  {compliance_count} compliance — $X/mo savings`.
- Run ID formula is fixed: `CLEAN-{YYYYMMDD}-{scope}-{sha256(rules.yaml)[:8]}`.
- All counts are integers; savings in USD with no decimals (round to nearest integer).

## Determinism Deviation

This PoC does **not** include `validate_query` in its tool allowlist per source spec (ratification #7).
The flow is `execute_query` directly (or `generate_query` → `execute_query` when `generate_hint` is
set) — there is no validate step.

KQL correctness is assured by pre-testing during development. Operators running this PoC live should
hand-verify `rules.yaml` KQL via the `validate_query` tool in another workspace if uncertain.

## Deploy-capable but effectively read-only

`create_template_deployment` appears in the tool allowlist for **shape conformance** with the
canonical fleet pattern only. **The agent MUST NEVER call it.** v1 PROPOSES templates by writing
them to `exports/proposed-pr/`; humans review and merge to a Git repo separately.
PR creation is conceptual and out of scope — see [Out of scope](#out-of-scope-future-enhancements).

## Schedule discipline

The `schedule` key in the runbook is **informational only**. v1 is invoked manually:

```
@weekly-cleanup scan for scope prod
```

Automated scheduling via GitHub Actions cron or Azure Pipelines is a future enhancement.

## How it works (end-to-end flow)

1. **Chat client routes the message.** VS Code Copilot Chat sees the `@weekly-cleanup` mention,
   loads [`.github/copilot/agents/weekly-cleanup.agent.md`](.github/copilot/agents/weekly-cleanup.agent.md)
   as the system prompt, and reads its `tools:` declarations to know which MCP tools to expose.
2. **Workspace MCP servers start.** The runtime reads [`.vscode/mcp.json`](.vscode/mcp.json),
   starts the ARM MCP server, and enumerates the 3-tool allowlist.
3. **LLM gets its toolbox.** The model sees the agent's hard rules, the SKILL.md procedure, the
   user prompt, and JSON schemas for the 3 allowed MCP tools.
4. **LLM follows skill step 1 — load inputs.** Reads `runbooks/prod.yaml` (scope, sub IDs, RG
   list, `iac_repo_path`, `orphan_threshold_days`, `savings_rate_map`).
5. **LLM computes `run_id` deterministically.** `CLEAN-{YYYYMMDD}-{scope}-{sha256(rules.yaml)[:8]}`.
6. **LLM enters the per-rule loop.** For each rule, takes the **literal** KQL from `rules.yaml`,
   injects the scope filter, and calls `execute_query`. No `validate_query` call.
7. **R002 defensive path.** If `execute_query` returns a `resourcechanges` table-not-found error,
   emits `STATUS=SKIPPED REASON=resourcechanges-unavailable` and continues.
8. **Findings are categorized and sorted.** Grouped by category (orphaned → drift → compliance);
   within each group sorted by estimated savings descending.
9. **Agent composes the PR content.** PR title in the pinned format; body contains the categorized
   cleanup table, savings summary, and ARM patch template references (`remediation/*.json`).
10. **PR markdown written to disk.** Rendered to `exports/proposed-pr/CLEAN-<run_id>.md`.
    No deployment is issued. GitHub PR creation is out of scope for v1.

## Install

1. Clone this folder and open it as a workspace in VS Code.
   The ARM MCP server is already declared at workspace scope in [`.vscode/mcp.json`](.vscode/mcp.json) —
   VS Code will prompt you to start it the first time you open chat.
   - If not yet authorized: click through <https://aka.ms/JoinARMMCP>.
   - For GitHub Copilot CLI users: copy the `Azure Resource Manager MCP Server` entry from
     `.vscode/mcp.json` into `~/.copilot/mcp.json`.
2. Sign in to Azure (`az login`) with Reader + Resource Graph Reader on the target scope.

> MCP server entry at workspace scope (`.vscode/mcp.json`):
>
> ```json
> {
>   "servers": {
>     "Azure Resource Manager MCP Server": {
>       "type": "http",
>       "url": "https://mcp.management.azure.com"
>     }
>   }
> }
> ```

## Configure your scope

`scope prod` maps to [`runbooks/prod.yaml`](runbooks/prod.yaml). Values live in the gitignored
`prod.values.yaml`.

### Two-file pattern

| File | Committed? | Contains |
|---|---|---|
| [`runbooks/prod.yaml`](runbooks/prod.yaml) | ✅ yes | Template with `${placeholder}` tokens. No real values. |
| `runbooks/prod.values.yaml` | ❌ **gitignored** | Your real subscription ID, RG names, IAC repo path. |
| [`runbooks/prod.values.yaml.example`](runbooks/prod.values.yaml.example) | ✅ yes | Schema reference — copy this to start. |

### First-time setup

1. Copy the example:
   ```powershell
   Copy-Item runbooks/prod.values.yaml.example runbooks/prod.values.yaml
   ```
2. Edit `prod.values.yaml` with real values (subscription ID, RG names, `iac_repo_path`).
3. Verify `.gitignore` excludes `*.values.yaml`. Run `git status` and confirm `prod.values.yaml`
   is NOT listed.

### Key runbook settings

| Setting | Default | Purpose |
|---|---|---|
| `iac_repo_path` | (required) | Local path to IaC repo root — used by R003 (NSG drift) and R006 (IaC coverage) |
| `orphan_threshold_days` | `30` | Days of inactivity for R002 orphan detection |
| `schedule` | `"0 9 * * 1"` | Informational cron — v1 is manually invoked |
| `savings_rate_map` | see prod.yaml | Estimated monthly USD cost per resource type |

## Acceptance criteria

| Criterion | Where it lives |
|---|---|
| Runs unattended on schedule | `runbooks/prod.yaml` `schedule` key (informational in v1; invoke manually) |
| Single PR per week with categorized diffs | `templates/output-pr-content.md` + `exports/proposed-pr/` |
| Never deploys; only proposes | Agent hard rules + this README |
| Savings estimate per item | `runbooks/prod.yaml` `savings_rate_map` |

## Out of scope (future enhancements)

- **GitHub PR creation** — composing the PR content is in scope for v1; actually opening a GitHub
  Pull Request requires a separate agent or GitHub Actions integration. The ARM MCP server does not
  provide GitHub PR APIs. Wire a workflow that triggers on a new file in `exports/proposed-pr/`
  and calls `gh pr create`.
- **Automated scheduling** — v1 is manually invoked. A GitHub Actions schedule or Azure Pipelines
  cron can automate the weekly `scan` trigger.
- **Auto-merge / auto-apply** — v1 is propose-only; humans review and apply ARM patches.
- **R002 Change Analysis enablement** — the `resourcechanges` table requires Azure Change Analysis
  to be enabled on the subscription. See ratification #1 for the `skip_if_unavailable` policy.
