# Reliability Posture Scorecard (ARM MCP PoC)

A Copilot CLI / VS Code chat agent that scores every workload in an Azure scope against  
a fixed set of SRE reliability rules and emits a **byte-near-identical report every time**  
it is run with the same scope and ruleset.

Backed by the [Azure Resource Manager MCP Server](https://aka.ms/JoinARMMCP).

## What it does

1.  Loads a fixed rule pack (`skills/reliability-scorecard/rules/rules.yaml`) — 12 weighted  
    reliability checks with **pre-canned ARG queries**.
2.  For every rule: `validate_query` → `execute_query` (ARM MCP).
3.  Aggregates findings per workload (default = resource group; configurable to a tag).
4.  Renders a report using a **fixed markdown template** (`templates/output-report.md`).
5.  Generates ARM patch templates for the top 3 gap types from `remediation/`.
6.  Writes a row to `exports/scorecard-trend.csv` for weekly trend tracking.

## Why the output is deterministic

*   Queries are NOT generated by the LLM at run time — they are read verbatim from YAML.
*   The skill instructs the agent to emit the report using a fixed template with no paraphrasing.
*   Scoring formula is fixed: `score = max(0, 100 - sum(weight of failed rules))`.
*   Sort orders, column headers, decimal precision, and section order are all pinned in `SKILL.md`.
*   Run ID is the input scope hash + UTC date — identical inputs → identical run ID.

## How it works (end-to-end flow)

What happens after you type `@scorecard run for scope prod` — from prompt, through MCP, through the LLM, to the rendered report.

1.  **Chat client routes the message.** VS Code Copilot Chat sees the `@scorecard` mention, loads [`.github/copilot/agents/scorecard.agent.md`](.github/copilot/agents/scorecard.agent.md) as the system prompt, and reads its `tools:` / `mcp:` declarations to know which tools to expose.
2.  **Workspace MCP servers start.** The runtime reads [`.vscode/mcp.json`](.vscode/mcp.json), sees the `Azure Resource Manager MCP Server` entry (`type: http`, `url: https://mcp.management.azure.com`), performs the MCP `initialize` handshake, and asks `tools/list`. The server returns its tool descriptors (`generate_query`, `validate_query`, `execute_query`, `get_resource_types`, `create_template_deployment`, `get_deployment`).
3.  **LLM gets its toolbox.** The model now sees the agent's hard rules, the SKILL.md procedure, the user prompt, and JSON schemas for every MCP tool. No Azure call has happened yet.
4.  **LLM follows skill step 1 — load inputs.** It reads [`runbooks/prod.yaml`](runbooks/prod.yaml) (scope, sub IDs, RG include list, `workload_key`) and [`rules/rules.yaml`](.github/copilot/skills/reliability-scorecard/rules/rules.yaml) (12 rule definitions with literal KQL).
5.  **LLM computes** `**run_id**` **deterministically.** `RPS-{YYYYMMDD}-prod-{sha256(rules.yaml)[:8]}` — plain string assembly, no model judgment.
6.  **LLM enters the per-rule loop (skill step 2).** For each rule it takes the **literal** KQL from `rules.yaml`, does string substitution to inject the scope filter from `prod.yaml` (sub IDs, RG list), and calls MCP `validate_query` with that string.
7.  **MCP** `**validate_query**` **round-trip.** The chat runtime sends a JSON-RPC `tools/call` over HTTP to `https://mcp.management.azure.com`. ARM MCP forwards to the ARG validator and returns "valid" or a syntax/auth error.
8.  **Conditional branch on validate result.**
    *   **Valid** → LLM calls MCP `execute_query` with the same KQL.
    *   **Invalid** → LLM marks the rule `INVALID` and **does not retry** (the agent contract forbids it). Skip to next rule.
9.  **MCP** `**execute_query**` **round-trip.** Same JSON-RPC path. The server runs the KQL against ARG using your signed-in Azure identity (`az login` token brokered by the runtime). Result rows come back as JSON.
10.  **LLM stores the rows** as `(rule_id, failing_resource_count, failing_resource_ids, weight, severity)` in working memory. No scoring yet.
11.  **Steps 6–10 repeat for all 12 rules.** Most chat runtimes parallelize independent tool calls, so several `validate_query` / `execute_query` pairs may be in flight at once. Each rule is independent because the KQL and scope are pre-baked.
12.  **LLM aggregates by workload (skill step 3a).** Failing rows grouped by the `workload_key` from `prod.yaml` (default = `resourceGroup`).
13.  **LLM computes the score (skill step 3b).** Pure arithmetic per workload: `score = max(0, 100 - Σ weight of failed rules)`. Formula is in SKILL.md.
14.  **LLM applies the fixed sort (skill step 3c).** Workloads sorted ascending by score, ties broken alphabetically. Top-3 gaps computed by `weight × failing_resource_count`, sorted desc, ties by `rule_id` asc.
15.  **LLM renders the output (skill step 4).** Loads [`templates/output-report.md`](.github/copilot/skills/reliability-scorecard/templates/output-report.md) and does literal `{{placeholder}}` substitution for `{{run_id}}`, `{{scope}}`, `{{generated_utc}}`, `{{ruleset_hash8}}`, summary counts, the bottom-10 table, the failing-checks table, and the top-3 gaps block. Layout is frozen.
16.  **LLM persists the artifacts.** Overwrites `exports/scorecard-prod-latest.md` with the rendered report and appends one CSV row to `exports/scorecard-trend.csv`.
17.  **LLM streams the result back to chat.** Same rendered markdown is returned as the assistant message — you see the report inline. No further MCP calls on the way out.
18.  **Conversation pauses, awaiting next command.** No state persists in the LLM beyond chat history. The next run starts again at step 1, re-reads the YAML, and — given the same inputs — produces the same `run_id` and identical numbers.

**Where the LLM ≠ the oracle:** steps 1, 4, 5, 6, 12, 13, 14, 15, 16 are rule-driven mechanics. The LLM is a workflow runner.  
**Where MCP does the heavy lifting:** steps 7 and 9 — validating and running the literal KQL against your live Azure subscription, with auth handled by the runtime, not the model.

## Install

1.  Clone this folder anywhere and open it as a workspace in VS Code.  
    The ARM MCP server is **already declared** at workspace scope in [`.vscode/mcp.json`](.vscode/mcp.json) — VS Code will prompt you to start it the first time you open the chat.
    *   If your VS Code account isn't yet authorized for the ARM MCP preview, also click through \<https://aka.ms/JoinARMMCP\> once.
    *   For GitHub Copilot CLI users: copy the `Azure Resource Manager MCP Server` entry from `.vscode/mcp.json` into `~/.copilot/mcp.json`.
2.  Sign in to Azure (`az login`) with Reader + Resource Graph Reader on the target scope.  
    For remediation deploys you also need Contributor on the target RGs.

> The MCP server entry at workspace scope (`.vscode/mcp.json`):
> 
> ```
> {
>   "servers": {
>     "Azure Resource Manager MCP Server": {
>       "type": "http",
>       "url": "https://mcp.management.azure.com"
>     }
>   }
> }
> ```

## Configure your scope (do this before first run)

`scope prod` is just the name of a runbook file — it maps to [`runbooks/prod.yaml`](runbooks/prod.yaml).  
The agent loads that YAML to know **which subscriptions** and **which resource groups** to query.  
You don't pass the sub on the command line — you put it in the YAML once, then `scope prod` is a friendly handle.

### Two-file pattern: template + values

To keep secrets and environment-specific IDs out of git, scope config is split in two:

| File | Committed? | Contains |
| --- | --- | --- |
| [`runbooks/prod.yaml`](runbooks/prod.yaml) | ✅ yes | Template with `${placeholder}` tokens. No real values. |
| `runbooks/prod.values.yaml` | ❌ **gitignored** | Your real subscription ID(s) and RG names. |
| [`runbooks/prod.values.yaml.example`](runbooks/prod.values.yaml.example) | ✅ yes | Schema reference — copy this to start. |

The skill substitutes every `${key}` in `prod.yaml` from `prod.values.yaml` at load time.  
If `prod.values.yaml` is missing, the agent aborts with a clear message — no guessing, no defaults.

### First-time setup

1.  **Copy the example to a real values file:**
    
    ```powershell
    Copy-Item runbooks/prod.values.yaml.example runbooks/prod.values.yaml
    ```
    
2.  **Edit** `**runbooks/prod.values.yaml**` and fill in real values:
    
    ```yaml
    subscription_id: "11111111-2222-3333-4444-555555555555"
    
    rg_include:
      - "payments-prod-rg"
      - "checkout-prod-rg"
    
    rg_exclude: []
    ```
    
3.  **Verify** `**.gitignore**` **excludes it** (it does — root `.gitignore` has `**/runbooks/*.values.yaml`). Run `git status` and confirm `prod.values.yaml` is NOT listed.
4.  **Don't edit** `**prod.yaml**` for normal use — it's a template. Only touch it if you want to change `workload_key` or add new placeholders.

Get your sub ID quickly:

```powershell
az account show --query id -o tsv
# or list all
az account list --query "[].{name:name, id:id}" -o table
```

### Common patterns

| You want… | Set this in `prod.values.yaml` |
| --- | --- |
| One specific sub | `subscription_id: "<sub-guid>"` |
| Score by app instead of by RG | edit `prod.yaml`: `workload_key: App` (where `App` is a tag name) |
| Only RGs containing "payments" | `rg_include: ["payments"]` |
| Skip a particular RG | add it to `rg_exclude` |

Matching is case-insensitive substring on RG name.

### Adding more scopes

Each scope is two files — a template + a values file. Both share the same base name:

```
runbooks/
  prod.yaml            ← committed template (placeholders)
  prod.values.yaml     ← gitignored, your values
  staging.yaml         ← committed template
  staging.values.yaml  ← gitignored, your values
```

Then run `@scorecard run for scope staging`. The run ID embeds the scope name, so trend rows in `exports/scorecard-trend.csv` stay separated per scope.

### Auth — yes, `az login` is enough

The ARM MCP server uses your signed-in Azure identity. Make sure:

1.  `az login` succeeded.
2.  `az account set --subscription <id>` if you have multiple and want a default.
3.  Your user has at least **Reader** + **Resource Graph Reader** on each sub listed. For the `remediate` flow you also need **Contributor** on the target RGs.

Quick check:

```powershell
az role assignment list --assignee (az account show --query user.name -o tsv) --all -o table
```


## Acceptance criteria mapping

| Criterion | Where it lives |
| --- | --- |
| ≥10 reliability rules with weighted scoring | `skills/reliability-scorecard/rules/rules.yaml` (12 rules) |
| Per-workload drill-down with raw ARG | `prompts/drilldown.prompt.md` + `templates/output-drilldown.md` |
| Auto-generated remediation ARM templates for top 3 gap types | `remediation/*.json` + `prompts/remediate.prompt.md` |
| Trend export so scores can be tracked weekly | `exports/scorecard-trend.csv` (one row per run) |
