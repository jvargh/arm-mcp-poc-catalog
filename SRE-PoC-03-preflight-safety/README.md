# Pre-flight Deployment Safety Check (SRE-PoC-3)

A Copilot CLI / VS Code chat agent that runs a fixed battery of Azure Resource
Graph (ARG) health-precondition queries **before every prod ARM deployment** and
**refuses to deploy** until all checks pass. Backed by the
[Azure Resource Manager MCP Server](https://aka.ms/JoinARMMCP).

## Purpose

Production deployments routinely fail because something in the target estate is
*already* unhealthy at the moment of deployment — an in-flight deployment is
holding a lock, a dependency Key Vault is in a `Failed` provisioning state, the
region is throttling, the operator is over quota, drift has crept in, or a
recent deployment is still failing. Those signals are all visible in ARG seconds
*before* `az deployment` is invoked, but no team has time to write and maintain
the queries by hand.

This PoC packages those queries as a **deterministic, reviewable rule pack**
(`skills/preflight-safety/rules/rules.yaml`) and runs them through the ARM MCP
server on demand. The agent is not allowed to invent queries, reorder rules,
or rephrase the report — every decision is reproducible from the rule-pack hash.

## Intended end state

When wired into your deployment workflow, a single chat command (or CLI call)
produces a report that is safe to drop into a PR, a change ticket, or a CI log:

* A fixed-format **markdown report** at `exports/preflight-<run_id>.md` with a
  per-rule status table, a one-line `Decision`, and remediation hints.
* A deterministic **`run_id`** of the form
  `PRE-{YYYYMMDD}-{scope}-{sha256(rules.yaml)[:8]}` that pins the report to the
  exact rule pack that produced it.
* A **gate**: when any check FAILs, the agent renders `FAIL — DEPLOY BLOCKED`
  and refuses to proceed to the deploy verb. Operators can override only by
  setting `force_deploy_flag: true` in the runbook *and* supplying a written
  justification — which writes a permanent audit entry to `exports/`.
* A **what-if deploy section** (v1) showing the exact template, parameters, and
  target RG that *would* be submitted. `create_template_deployment` is never
  called by the agent in v1 — operators run `az deployment group create`
  themselves once the gate is green.

What success looks like in practice: every prod deploy is preceded by a
green-lit, archived preflight report; every blocked deploy ships with a
machine-readable list of exactly which resources to fix and why.

## What it does

1. Loads a fixed rule pack (`skills/preflight-safety/rules/rules.yaml`) — 9
   preflight checks with **pre-canned ARG queries**.
2. For every active rule: `validate_query` → `execute_query` (ARM MCP). Rules
   run in **`rule_id` ascending order** (R001 first) within a configurable
   wall-clock budget.
3. Records one of five statuses per rule:
   * **PASS** — query returned 0 rows.
   * **FAIL** — query returned ≥ 1 row (a violation; up to 25 resource IDs are
     captured for the failing-resources detail block).
   * **SKIPPED** — `skip_if_unavailable: true` AND the underlying ARG table is
     unavailable, or quota limits are unconfigured (R005).
   * **INVALID** — `validate_query` rejected the rule's KQL, or the query
     errored in a way the rule cannot recover from.
   * **TIMEOUT** — the wall-clock budget (`preflight_timeout_seconds`) was
     exhausted before this rule ran.
4. Renders a deterministic preflight-results report via a fixed markdown
   template.
5. **Gates the deployment**: refuses to deploy when any check FAILs, unless
   `force_deploy_flag: true` is set in the runbook (an audit entry is written
   to `exports/`).
6. In v1: renders a "Would deploy (NOT EXECUTED)" outcome — does not call
   `create_template_deployment`.

## Why the output is deterministic

* Queries are NOT generated by the LLM at run time — read verbatim from YAML.
* The skill instructs the agent to emit the report using a fixed template.
* Check order is pinned: `rule_id` ascending (R001, R002 … R009).
* PASS / FAIL / SKIPPED / INVALID / TIMEOUT logic is rule-driven, not
  LLM-judged. Zero rows = PASS, non-zero = FAIL.
* `run_id` format: `PRE-{YYYYMMDD}-{scope}-{sha256(rules.yaml)[:8]}` — pure
  string assembly, no model call.
* Time budget enforced: total wall-clock for all checks ≤
  `preflight_timeout_seconds` (default 30s). On exhaustion, remaining rules
  are recorded as **TIMEOUT** and a budget-exceeded warning is appended to
  the report.

## Determinism deviation

This PoC **includes** `validate_query` in its tool allowlist per the source
spec. The `validate_query` → `execute_query` pattern is used on the hot path.

## How it works (end-to-end flow)

1. **Chat client routes the message.** VS Code sees `@preflight-safety`, loads
   `.github/copilot/agents/preflight-safety.agent.md` as the system prompt.
2. **MCP server starts** from `.vscode/mcp.json`. The ARM MCP server descriptor
   lists the 5 tools in the allowlist.
3. **LLM reads runbook** (`runbooks/prod.yaml` + `prod.values.yaml`), extracts
   `subscriptions`, `rg_include`, `rg_exclude`, `preflight_rules_per_env`,
   `force_deploy_flag`, `preflight_timeout_seconds`, `quota_limits`.
4. **LLM computes `run_id`** deterministically:
   `PRE-{YYYYMMDD}-{scope}-{hash8}`.
5. **LLM enters the per-rule loop** in `rule_id` order. For each rule it calls
   `validate_query` then `execute_query` with the literal KQL from
   `rules.yaml`.
6. **SKIP handling:** if `skip_if_unavailable: true` AND the query errors with
   table-not-found / table-unavailable OR returns no data with an error
   indicator — the check is SKIPPED (non-fatal). Affected rules: R001, R004,
   R005, R009.
7. **Decision:** the gate counts only **FAIL** as a blocker. SKIPPED, INVALID,
   and TIMEOUT outcomes are surfaced in the report but do not by themselves
   block:
   * `checks_fail == 0` → **PASS — DEPLOY ALLOWED**
   * `checks_fail > 0` AND `force_deploy_flag == false` →
     **FAIL — DEPLOY BLOCKED**
   * `checks_fail > 0` AND `force_deploy_flag == true` →
     **FORCE — DEPLOY WITH AUDIT WARNING** (audit entry written to `exports/`)
8. **v1 deploy path:** LLM renders the "Would deploy (NOT EXECUTED in v1)"
   section. `create_template_deployment` is **never called**.
9. **Report rendered** via `templates/output-preflight-results.md` (preflight
   verb) or `templates/output-report.md` (deploy verb).

## Install

1. Clone this folder and open it as a workspace in VS Code.
   `.vscode/mcp.json` declares the ARM MCP server — VS Code will prompt to
   start it.
   * If not yet authorized: <https://aka.ms/JoinARMMCP>
   * GitHub Copilot CLI: copy the server entry into `~/.copilot/mcp.json`.
2. Sign in (`az login`) with **Reader + Resource Graph Reader** on the target
   scope.

## Configure your scope

`scope prod` maps to `runbooks/prod.yaml`. Two-file pattern — same as the
reference implementation:

| File | Committed? | Contains |
|---|---|---|
| `runbooks/prod.yaml` | ✅ yes | Template with `${placeholder}` tokens. No real values. |
| `runbooks/prod.values.yaml` | ❌ **gitignored** | Your real subscription ID, RG names, quota limits. |
| `runbooks/prod.values.yaml.example` | ✅ yes | Schema reference — copy this to start. |

### First-time setup

```powershell
Copy-Item runbooks/prod.values.yaml.example runbooks/prod.values.yaml
# Edit prod.values.yaml with real values
```

Important keys in `prod.values.yaml`:

```yaml
subscription_id: "11111111-2222-3333-4444-555555555555"
rg_include: ["payments-prod-rg"]
rg_exclude: []
deployment_target_rg: "payments-prod-rg"

# Quota limits for R005 (keep in sync with az vm list-usage):
quota_limits:
  vm_cores_per_region: 100
  public_ip_addresses: 50
  network_interfaces: 200
  storage_accounts: 250
```

Set all quota limits to `0` to SKIP R005 quota checks.

## Runbook keys reference

| Key | Type | Default | Description |
|---|---|---|---|
| `subscriptions` | list | required | Azure subscription GUIDs to query |
| `rg_include` | list | `[]` | RG name substrings to include (case-insensitive) |
| `rg_exclude` | list | `[]` | RG name substrings to exclude |
| `deployment_target_rg` | string | required | RG where the ARM template deploys |
| `preflight_rules_per_env` | map | all rules | Per-env rule_id filter |
| `force_deploy_flag` | bool | `false` | Override FAIL and deploy with audit warning |
| `preflight_timeout_seconds` | int | `30` | Total wall-clock budget for all checks |
| `quota_limits` | map | all 0 | Known quota limits for R005 |

## Run

VS Code chat:

```
@preflight-safety preflight scope prod
```

GitHub Copilot CLI:

```
copilot -p "Run preflight safety check for scope prod"
```

> **CLI users:** see [Copilot CLI usage notes](../README.md#copilot-cli-usage-notes) — `gh copilot` has a quoting bug on Windows when `copilot` lives on a path with spaces, `@agent` mentions don't work in the CLI, and first runs take a few minutes.

Deploy (after PASS):

```
@preflight-safety deploy scope prod template templates/my-template.json params templates/my-template.parameters.json
```

Check deployment status:

```
@preflight-safety status
```

## Preflight Rules

| Rule ID | Title | Severity | Skip if unavailable |
|---|---|---|---|
| R001 | Active resource health incidents in scope | critical | ✅ yes |
| R002 | Overlapping deployments already Running | high | no |
| R003 | Dependency resources not in Succeeded state | high | no |
| R004 | Recent throttling/errors (resourcechanges, 15min) | high | ✅ yes |
| R005 | Quota headroom | medium | ✅ yes |
| R006 | Resources lacking `iac-managed` tag (drift) | medium | no |
| R007 | Resources missing required deployment tags | medium | no |
| R008 | Failed deployments in the last 1 hour | high | no |
| R009 | Region capacity signal | low | ✅ yes |

SKIP rules (R001, R004, R005, R009) carry `skip_if_unavailable: true` per
ratification #1 (R004: `resourcechanges` table may not be enabled),
ratification #2 (R001: `HealthResources` may not be queryable), and Bishop's
notes (R005/R009: ARG cannot determine quota limits or region capacity
ceilings).

> **Failing-resources count caveat.** ARG paginates result sets. When a query
> returns more than ~200 rows the agent records the count as `≥200 (ARG page
> cap)` rather than scrolling through every page. The decision is unaffected
> (any `≥1` is FAIL), but operators triaging drift should treat the count as a
> floor, not the true total. See "What to expect from a real run" below.

## What to expect from a real run

A live run on the development subscription
(`exports/preflight-PRE-20260513-prod-a18f2992.md`) produced this outcome on a
drift-heavy estate with the default 30s budget:

| Metric | Value |
|---|---|
| Checks passed | 5 (R001–R005) |
| Checks failed | 2 (R006, R007) |
| Checks skipped / invalid / timed-out | 2 (R008, R009 — TIMEOUT) |
| Decision | **FAIL — DEPLOY BLOCKED** |

Concrete lessons from that run:

1. **`R006` (drift) and `R007` (required tags) FAIL first** in any subscription
   that has not been onboarded to a tagging convention. Both rules return
   `≥200 (ARG page cap)` against unmanaged estates. This is the design — those
   rules exist to surface drift — but operators should expect to spend their
   first iteration fixing tags rather than chasing other rules.
2. **The 30s budget can be exhausted by drift-heavy estates.** The live run
   exhausted the budget after R007, leaving R008 and R009 as TIMEOUT. The
   report still rendered with a `> ⚠️ Budget warning` block, and TIMEOUT did
   *not* by itself flip the gate to BLOCK — but the operator lost visibility
   into recent failed deployments and region capacity for that run.
3. **The gate fires on FAIL only.** TIMEOUT and SKIPPED do not block. So
   `force_deploy_flag` is reserved for genuine FAILs (e.g., drift you
   acknowledge and will remediate post-deploy), not for budget shortfalls —
   raise the budget instead.
4. **Reports are saved to `exports/`** with the deterministic `run_id` in the
   filename, so the same operator can compare runs day-over-day and PR
   reviewers can diff them.

A simulated run showing both the FAIL+block path and the PASS+would-deploy
path is included at `exports/test-run.md`.

## Tuning for large or drift-heavy estates

If the live run shows TIMEOUT on the lower-`rule_id` rules (R007–R009) or the
budget warning fires every run:

* **Narrow `rg_include`** to the specific RG(s) being deployed to. The default
  shape of the rules scans every RG in the subscription that matches the
  include filter; tightening that list is the highest-leverage knob.
* **Raise `preflight_timeout_seconds`** in the runbook. 60s is reasonable for
  estates with hundreds of resources; 120s is the practical ceiling before a
  CI/PR reviewer loses patience.
* **Subset rules per environment** via `preflight_rules_per_env`. For
  `staging` you might run only `[R001, R002, R003, R008]`; reserve the full 9
  for `prod`.
* **Fix tags first.** R006 and R007 will dominate failing-resource counts in
  any un-tagged subscription. Run them once, fix the listed resources (or set
  the missing tags via Azure Policy), and they will drop to PASS.

## What-if only (locked decision + ratification #3)

v1 does **not** invoke `create_template_deployment`. The `deploy` verb renders
a "Would deploy (NOT EXECUTED in v1)" appendix showing the template and
parameters that **would** be submitted. This honors the locked decision:
*what-if templates only — never call `create_template_deployment` in any test
path.*

and FAIL+block flows, and `exports/preflight-PRE-20260513-prod-a18f2992.md`
