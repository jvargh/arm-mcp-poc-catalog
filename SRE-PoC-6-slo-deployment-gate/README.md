# SLO-Aware Deployment Gate (SRE-PoC-6)

A Copilot CLI / VS Code chat agent that **gates deploys** to services whose SLO error
budget is already burned — using ARM Resource Graph (ARG) to fetch App Insights /
Log Analytics metadata and component tags, then evaluating budget against a runbook
threshold.

Backed by the [Azure Resource Manager MCP Server](https://aka.ms/JoinARMMCP).

## What it does

1. Loads a fixed rule pack (`skills/slo-deployment-gate/rules/rules.yaml`) — 3 SLO
   evaluation rules with **pre-canned ARG queries**.
2. For every rule: `generate_query` → `execute_query` (ARM MCP).
3. Reads SLO budget from runbook `slo_targets` block (v1 simulated; see Known Limitations).
4. Computes a deterministic **ALLOW** or **BLOCK** gate decision.
5. On ALLOW: emits a **what-if deploy notice** (v1 never issues a real deployment).
6. On BLOCK: gates the user's template and explains why.
7. Accepts bypass with a valid CR or incident reference; writes audit log to `exports/`.

## Why the output is deterministic

- Queries are NOT generated by the LLM at run time — they are read verbatim from YAML.
- Gate decision is pure arithmetic: `budget_pct > threshold → ALLOW`, `≤ threshold → BLOCK`.
- Timeout = auto-deny (BLOCK). No ambiguous intermediate state.
- Sort orders, column headers, and decimal precision (1 decimal, e.g. `72.4%`) are pinned in `SKILL.md`.
- Run ID is deterministic: `SLO-{YYYYMMDD}-{scope}-{sha256(rules.yaml)[:8]}`.

## How it works (end-to-end flow)

1. **Chat client routes the message.** VS Code Copilot Chat sees the `@slo-deployment-gate`
   mention, loads `.github/copilot/agents/slo-deployment-gate.agent.md` as the system prompt.
2. **Workspace MCP server starts.** Runtime reads `.vscode/mcp.json`, sees the
   `Azure Resource Manager MCP Server` entry, performs MCP `initialize` handshake.
3. **Step 1 — Load configuration.** Agent reads `runbooks/prod.yaml` (with `.values.yaml`
   substitution) and `rules/rules.yaml`. Computes `run_id`.
4. **Step 2 — Rule evaluation loop.** For each rule: `generate_query` → `execute_query`.
   R001 resolves the service to a workspace resource ID by `slo_service` tag.
   R002 checks workspace properties for a `slo_budget_pct` tag (absent in most environments).
   R003 checks ResourceHealth for active incidents.
5. **Step 3 — Budget evaluation.** Reads `simulated_budget_pct` from runbook (v1).
   Emits `STATUS=OUT_OF_SCOPE REASON=arg-cannot-read-metrics WORKSPACE=<id>`.
6. **Step 4 — Gate decision.** `budget_pct > threshold → ALLOW`, `≤ threshold → BLOCK`.
   Active incident (R003) → BLOCK if `block_on_active_incident: true`.
7. **Step 5 — Output.** Renders `output-gate-result.md` via literal `{{placeholder}}`
   substitution. Writes to `exports/gate-<run_id>.md`.
8. **`deploy` mode.** On ALLOW: renders `output-report.md` with would-deploy notice.
   No real `create_template_deployment` call in v1.

## Install

1. Clone this folder anywhere and open it as a workspace in VS Code.
   The ARM MCP server is **already declared** at workspace scope in [`.vscode/mcp.json`](.vscode/mcp.json).
   - If your VS Code account isn't yet authorized for the ARM MCP preview, click through
     <https://aka.ms/JoinARMMCP> once.
   - For GitHub Copilot CLI users: copy the `Azure Resource Manager MCP Server` entry
     from `.vscode/mcp.json` into `~/.copilot/mcp.json`.
2. Sign in to Azure (`az login`) with Reader + Resource Graph Reader on the target scope.

> The MCP server entry at workspace scope (`.vscode/mcp.json`):
>
> ```json
> {
>   "servers": {
>     "Azure Resource Manager MCP Server": {
>       "type": "http",
>       "url": "https://mcp.management.azure.com"
>     }
>   }
> }
> ```

## Configure your scope (do this before first run)

`scope prod` maps to `runbooks/prod.yaml`. The agent loads that YAML to know
**which subscriptions** and **which services/SLO targets** to evaluate.

### Two-file pattern: template + values

| File | Committed? | Contains |
|---|---|---|
| `runbooks/prod.yaml` | ✅ yes | Template with `${placeholder}` tokens + SLO targets. |
| `runbooks/prod.values.yaml` | ❌ **gitignored** | Your real subscription ID(s) and RG names. |
| `runbooks/prod.values.yaml.example` | ✅ yes | Schema reference — copy this to start. |

### First-time setup

1. **Copy the example to a real values file:**

   ```powershell
   Copy-Item runbooks/prod.values.yaml.example runbooks/prod.values.yaml
   ```

2. **Edit `runbooks/prod.values.yaml`** and fill in real values:

   ```yaml
   subscription_id: "11111111-2222-3333-4444-555555555555"

   rg_include:
     - "payments-prod-rg"

   rg_exclude: []
   ```

3. **Add your services** to `slo_targets` in `runbooks/prod.yaml`:

   ```yaml
   slo_targets:
     my-service:
       budget_threshold_pct: 50.0
       window_days: 30
       approval_required_below_pct: 75.0
       simulated_budget_pct: 65.0   # replace with live integration for prod
   ```

4. **Tag your App Insights components** with `slo_service: <service-name>` so R001 can
   resolve them. Example with Azure CLI:

   ```powershell
   az resource tag --ids /subscriptions/.../resourceGroups/.../providers/microsoft.insights/components/my-app-insights --tags slo_service=my-service
   ```

## Run

VS Code chat:

```
@slo-deployment-gate gate scope prod service payments-api
```

Gate + would-deploy (ALLOW path):

```
@slo-deployment-gate deploy scope prod service payments-api template infra/main.json
```

Check last gate result:

```
@slo-deployment-gate status scope prod service payments-api
```

Bypass a BLOCK (requires CR or incident ref):

```
@slo-deployment-gate deploy scope prod service checkout-api template infra/main.json bypass CR-001234
```

GitHub Copilot CLI:

```
gh copilot -p "Gate deployment for service payments-api in scope prod"
```

## Acceptance criteria mapping

| Criterion | Where it lives |
|---|---|
| Service ↔ SLO mapping by tag | R001 in `rules.yaml` + `slo_service` tag convention |
| Budget calc input pluggable | `budget_source` + `simulated_budget_pct` in `prod.yaml` |
| Approval workflow with timeout | `approval_timeout_minutes` in `prod.yaml`; SKILL.md Step 3 |
| Bypass requires incident or CR ref | `gate.prompt.md` hard rule; SKILL.md Step 5; `bypass-audit.jsonl` |

## Determinism Deviation

> **This PoC does not include `validate_query` in its tool allowlist per source spec.**
>
> Per ratification #7 (`.squad/decisions/inbox/copilot-bishop-ratifications-2026-05-12.md`),
> `validate_query` is NOT listed in the tool allowlist for SRE-PoC-6. KQL correctness is
> assured by pre-testing during development. Operators running this PoC live should
> hand-verify `rules.yaml` KQL via the `validate_query` tool in another workspace if uncertain.
>
> The skill goes directly: `generate_query` → `execute_query` (skipping the validate step).

## Known limitations

1. **SLO error budget % is NOT queryable via ARG.** ARG can locate the App Insights /
   Log Analytics workspace resource (R001) and read tag/property metadata (R002), but
   **cannot read live metric values** such as error rate or availability percentage.
   Output always includes:
   ```
   STATUS=OUT_OF_SCOPE REASON=arg-cannot-read-metrics WORKSPACE=<resource-id>
   ```
   with a pointer to the workspace resource ID for operator investigation.

2. **v1 budget source is simulated.** In v1 the budget percentage is read from
   `slo_targets.<service>.simulated_budget_pct` in the runbook. This is a hardcoded
   test value for PoC purposes. Production wiring (Azure Monitor query, Prometheus scrape,
   or external SLO platform API call) is **out of scope for this ARM MCP PoC**.

3. **No real deployments in v1.** Per locked decision + ratification #3, `create_template_deployment`
   is never actually called. The agent simulates the would-deploy outcome on ALLOW.

4. **ResourceHealth table availability.** R003 uses `resourceHealthResources`, which may
   not be enabled in all subscriptions. If unavailable, R003 emits
   `STATUS=SKIPPED REASON=resourcechanges-unavailable` and continues (non-blocking).
